# Telegram Media Saver Bot

Бот, которому пересылаешь сообщения с медиа (фото, видео, музыка, документы)
или просто текстом. Он скачивает их пакетами и раскладывает по папкам на
сервере — забирать файлы по SFTP/rsync вместо медленного скачивания по
одному из клиента Telegram. Текстовые сообщения сохраняются как `.md`-файлы
с сохранением форматирования (жирный, курсив, ссылки, списки и т.д.) —
конвертация из Telegram entities в markdown делает сам Pyrogram.

## Настройка

1. Получите `API_ID` и `API_HASH` на https://my.telegram.org (раздел "API
   development tools").
2. Создайте бота через [@BotFather](https://t.me/BotFather) и получите
   `BOT_TOKEN`.
3. Узнайте свой Telegram user ID (например, через
   [@userinfobot](https://t.me/userinfobot)) и впишите его в
   `ALLOWED_USER_IDS` (через запятую, если владельцев несколько).
4. Скопируйте `.env.example` в `.env` и заполните все значения:

   ```bash
   cp .env.example .env
   ```

5. Запустите бота:

   ```bash
   docker compose up -d --build
   ```

   Убедитесь, что папка `./storage` на хосте доступна для записи контейнеру.

   Чтобы остановить и удалить контейнер после работы:

   ```bash
   docker compose down
   ```

   Без Docker (разовый запуск или systemd-сервис) — см. [`DEPLOY.md`](DEPLOY.md).
   В этом случае `.env` (со значениями для Docker, `STORAGE_DIR=/storage`)
   держите отдельно от `.env.local` (для локального запуска, `STORAGE_DIR`
   без начального слэша) — так контейнерный и локальный конфиг не мешают
   друг другу.

6. Откройте чат с ботом в Telegram и нажмите Start — бот пришлёт приветствие
   с краткой инструкцией и кнопкой "❓ Справка". Эту же справку можно вызвать
   в любой момент командой `/help` или кнопкой ниже сообщения.
7. Перешлите боту файлы или текст. Пока пакет активен, статусное сообщение раз в ~5
   секунд показывает, сколько файлов уже сохранено и какой файл скачивается
   прямо сейчас (с процентом). Файлы одного пакета скачиваются строго по
   одному, не параллельно.
8. Завершите пакет кнопкой "✅ Завершить пакет" или дождитесь `BATCH_TIMEOUT`
   секунд без новых файлов — бот пришлёт итог с путём к папке.

9. Забирайте файлы с сервера из каталога `./storage/<дата>_<время>/` по
   SFTP/SMB/rsync. В каждой папке лежит `manifest.json` со списком файлов
   (исходное имя, итоговое имя, тип, размер, дата, подпись, ошибки).

## Переменные окружения

| Переменная       | Назначение                                              |
|-------------------|---------------------------------------------------------|
| `API_ID`          | MTProto API ID с my.telegram.org                        |
| `API_HASH`        | MTProto API hash с my.telegram.org                      |
| `BOT_TOKEN`       | Токен бота от @BotFather                                |
| `ALLOWED_USER_IDS`| Белый список Telegram ID через запятую                  |
| `STORAGE_DIR`     | Каталог для файлов внутри контейнера (`/storage`)       |
| `BATCH_TIMEOUT`   | Сек. без новых файлов до авто-закрытия пакета (по умолч. 30) |
| `OWNER_USER_ID`   | Telegram ID владельца бота: получает сообщения, которые бот не смог обработать. Обязательно — Telegram не сообщает боту, кто его владелец |
| `ARCHIVE_CHATS`   | Архив групп: `<chat_id>[/<topic_id>]=<папка>` через `;`; пусто — выключен |
| `ARCHIVE_TZ`      | Часовой пояс архива (по умолч. `Europe/Berlin`)         |
| `ARCHIVE_SESSION_DIR` | Папка сессии MTProto для догона пропущенного (по умолч. `sessions`) |
| `ELEVENLABS_API_KEY` | Ключ ElevenLabs для расшифровки голосовых; пусто — без расшифровки |
| `STT_MODEL`       | Модель ElevenLabs Scribe для расшифровки (по умолч. `scribe_v2`) |
| `TRANSCRIBE_MAX_SECONDS` | Не расшифровывать длиннее, сек (по умолч. 1800) |
| `SPEAKER_MODEL`   | Модель Claude для смыслового прохода по расшифровке: реплики и кто их говорит (по умолч. `sonnet`); `off` — без модели, реплики по паузам, «Спикер N» |
| `CLAUDE_BIN`      | Путь к Claude Code CLI (по умолч. из `PATH`, затем `~/.local/bin/claude`) |
| `CONFIG_FILE`     | Путь к env-файлу для горячей подгрузки настроек архива; пусто — только при старте |

## Архив группового чата

Тот же бот можно добавить в группу: он молча (ничего не пишет в чат)
сохраняет все сообщения группы в markdown-архив. Включается переменной
`ARCHIVE_CHATS` (`<chat_id>=<папка>`, несколько через `;`); группы не из
списка игнорируются (их id пишется в лог). Личка работает как раньше.

В группе с темами (forum) можно архивировать одну тему: `<chat_id>/<topic_id>=<папка>`
(topic_id — номер из ссылки на тему `t.me/c/<id>/<topic_id>`, General — `1`).
Остальные темы этой группы пропускаются. Без `/<topic_id>` пишется вся группа.

Что сохраняется: текст с форматированием (CommonMark, свой конвертер
entities — диалект `.markdown` Pyrogram для архива не годится), rich-сообщения,
фото/видео/документы/аудио/голосовые/кружки (скачиваются в `media/`),
ответы (на какое сообщение, цитата), пересылки, правки, опросы, места,
контакты, служебные события. Голосовые, аудио, кружки и видео расшифровываются
через ElevenLabs Scribe (`ELEVENLABS_API_KEY`; без ключа — только файлы).
Модель — `STT_MODEL` (по умолчанию `scribe_v2`); у каждой расшифровки в
`messages.jsonl` записано, какой моделью она сделана (`transcript_model`).
Автоматически узнать новейшую модель нельзя: `/v1/models` ElevenLabs отдаёт
только модели синтеза и преобразования голоса, моделей Scribe там нет.
Пустой ответ (тишина, шум, слишком тихо) помечается «речь не распознана».

Из Scribe берётся максимум деталей: разметка по голосам (`diarize`),
таймкоды до символа (`timestamps_granularity=character`: у каждого слова
`start`, `end`, `speaker_id`, `logprob`, `characters`) и звуковые события
(`tag_audio_events` — смех, шум; в текст архива не попадают). Полный ответ
API лежит рядом с файлом — `media/<id>_transcript.json` (в `messages.jsonl`
поле `transcript_raw` — путь к нему), чтобы журнал оставался лёгким.

Потом — смысловой проход моделью Claude через локальный Claude Code CLI
(`claude -p`, его собственный вход; `SPEAKER_MODEL`, `CLAUDE_BIN`). Слова
режутся на мелкие пронумерованные фрагменты (смена голоса, конец
предложения, пауза), модель видит их с метками голоса и таймкодами, список
участников чата и последние сообщения и возвращает только разбиение:
`[{first, last, speaker}]` — какие фрагменты подряд составляют одну реплику
по смыслу (без разрыва посреди фразы) и кто её говорит; ошибку разметки
голосов она может исправить, переназначив фрагмент другому человеку. Текст
остаётся дословно от ElevenLabs — модель слов не пишет. Ответ проверяется
(все фрагменты по порядку, без пропусков и наложений); невалидный ответ или
ошибка — запасной путь: реплики по смене голоса и паузам от 2 с, имена
голосам угадывает модель отдельным запросом, а без неё — «Спикер 1»,
«Спикер 2». Короткое голосовое (до 2 мин) с одним голосом — без модели,
говорит отправитель. `sonnet` по умолчанию: `haiku` на тестовом созвоне
примерно в половине запусков склеивал вопрос и ответ в одну реплику.

В архиве — реплики `[м:сс] Имя: текст`. В `messages.jsonl` —
`transcript_segments` (`start`, `end`, `speaker`, `text`; `speaker` — имя
после смыслового прохода или `speaker_N` после запасного),
`transcript_speakers` (`speaker_N` → имя) и `transcript_refined` (был ли
смысловой проход). Старые расшифровки (до таймкодов) остаются сплошным
текстом; переделать выбранные (`--refine-only` — только смысловой проход по
сохранённому `transcript_raw`, без нового запроса в ElevenLabs):

```bash
uv run --env-file .env.local python -m mediasaver.archive.retranscribe <папка архива> <id> [<id> …] [--refine-only]
```

Структура папки чата:

```
messages.jsonl   журнал: строка = частичная запись {id, поля}, поздние
                 строки дополняют ранние (правка, расшифровка) — источник истины
media/           файлы, <id сообщения>_<имя>; <id>_transcript.json — полный
                 ответ Scribe к расшифровке
days/YYYY-MM-DD.md  сообщения дня (время — ARCHIVE_TZ), якоря #m<id>,
                 ответы — ссылками на исходное сообщение
index.md         список дней со счётчиками
chat.json        название чата и темы, scanned_until — докуда прочитана история
```

Чтобы бот видел все сообщения, а не только команды: в @BotFather
`/setprivacy` → бот → Disable, затем удалить бота из группы и добавить снова
(или сделать админом).

История подтягивается сама: при каждом старте бот дочитывает сообщения,
которых нет в архиве — с начала чата при первом запуске, дальше от
последнего просмотренного номера (`scanned_until` в `chat.json`). Листать
историю ботам Telegram не даёт, но сообщения по номерам отдаёт, а номера в
супергруппе идут подряд: бот запрашивает их пачками по 200, ждёт, сколько
требует Telegram (flood wait), и делает паузу между пачками. После загрузки
расшифровываются голосовые, у которых ещё нет расшифровки. Так архив
включает и сообщения до добавления бота, и пришедшие, пока он был выключен.

Настройки архива подхватываются без перезапуска, если `CONFIG_FILE`
указывает на env-файл бота (например `CONFIG_FILE=.env.local`). Бот проверяет
файл при каждом сообщении группы и раз в 15 секунд; когда он изменился,
применяет `ARCHIVE_CHATS` (новые чаты/темы сразу догружают историю, убранные
отключаются), `ARCHIVE_TZ` (архив перерисовывается), `STT_MODEL` (для новых расшифровок;
сделанные не переделываются), `ELEVENLABS_API_KEY` и
`TRANSCRIBE_MAX_SECONDS` (расшифровываются ожидавшие голосовые; при смене
ключа заново пробуются и те, что упали с ошибкой — например, 401 от старого ключа). Ошибка в
файле пишется в лог, бот остаётся на прежних настройках. Токен бота,
`API_ID`/`API_HASH`, `ARCHIVE_SESSION_DIR` и обновления кода по-прежнему
требуют перезапуска.

Для обычной группы (не супергруппы) или если история скрыта от новых
участников, есть импорт экспорта Telegram Desktop (чат → ⋮ → Export chat
history, формат JSON, с фото, файлами и голосовыми):

```bash
uv run --env-file .env.local python -m mediasaver.archive.tg_export_import <папка экспорта> <папка архива> --transcribe
```

Запускать из корня репозитория и именно как модуль (`-m`): запуск файлом
`python mediasaver/archive/tg_export_import.py` упадёт на импортах.

Сообщения, уже записанные ботом, импорт не трогает (id совпадают).

## Неподдерживаемые сообщения

Если пересланное сообщение не подходит ни под один поддерживаемый тип
(стикер, опрос, геолокация, новый формат Telegram и т.п.), бот не молчит:
отвечает на него, что сообщение пропущено, и спрашивает, переслать ли его
разработчику. По кнопке «Да» оригинал пересылается владельцу бота
(`OWNER_USER_ID`) вместе с информацией, кто его прислал и какого оно типа.
Под отчётом у владельца есть кнопка «✅ Исправлено»: когда поддержка
добавлена, нажатие отправляет пользователю ответом на его исходное сообщение
уведомление, что его можно переслать снова.

Сообщения, отправленные боту напрямую (не пересланные: набранный текст,
стикер из панели, неизвестная команда), бот не сохраняет — это не ошибка,
поэтому разработчику они не уходят, но бот отвечает подсказкой, что нужно
пересылать сообщения.

Rich-сообщения (структурированный текст Telegram: списки, заголовки,
таблицы — у них пустой обычный текст) сохраняются как `.md`, как и обычный
текст. Встроенные в них фото, видео и аудио скачиваются рядом с `.md`
(`text_<дата>_<id>_<n>.<ext>`): фото вставлены в документ картинкой
(`![фото](...)`), остальное — ссылкой по относительному пути. В
`manifest.json` такие файлы перечислены в поле `attachments` записи `.md`.

## Разработка и тесты

```bash
uv sync            # runtime + dev-зависимости из uv.lock в .venv
uv run pytest -v
```

Зависимости объявлены в `pyproject.toml`, точные версии — в `uv.lock`.
`requirements.txt` генерируется (его читает Dockerfile), руками не править:

```bash
uv lock                                    # после правки зависимостей
uv lock --upgrade-package <пакет>          # обновить один пакет
uv export --no-dev --no-hashes --no-emit-project -o requirements.txt
```

Структура: `bot.py` (точка входа) и пакет `mediasaver/` — `core/` (config,
storage, batch_manager, downloader), `media/` (text_export, rich_markdown,
rich_media, unsupported), `archive/` (архив чата, tg_markdown, transcribe,
segments, refine, speakers, claude_cli, retranscribe, tg_export_import). Тесты зеркалят пакеты в `tests/`. Все модули пакета
покрыты юнит-тестами без обращения к реальному Telegram
API. `bot.py` проверен лёгким smoke-тестом, который собирает приложение без
сетевых вызовов.

Дополнительно (опционально) — ручная интеграционная проверка на тестовом
боте: поднять `docker compose up -d --build`, проверить:
- `/start` присылает приветствие с кнопкой "❓ Справка"; `/help` и сама кнопка
  показывают тот же текст в любой момент;
- при пересылке нескольких файлов подряд статусное сообщение обновляется
  раз в ~5 секунд и показывает текущий скачиваемый файл с процентом;
- файлы одного пакета скачиваются по одному, не параллельно;
- кнопка "✅ Завершить пакет" закрывает пакет немедленно;
- при отсутствии новых файлов пакет закрывается сам через `BATCH_TIMEOUT`
  секунд;
- при пересылке большого числа файлов подряд (20+) итоговый счётчик и
  `./storage/<пакет>/manifest.json` точно совпадают с реальным числом файлов
  на диске — это регрессионная проверка бывшего бага с заниженным счётом;
- пересылка текстового сообщения с форматированием (жирный/курсив/ссылка)
  сохраняется как `.md`-файл, и разметка в нём соответствует оригиналу.
